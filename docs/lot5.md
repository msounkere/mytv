# Lot 5 — Conversion du direct (regression par rapport a l'ancien service mytv-flux)

Constat (recette reelle 2026-10-15, code ancien : /opt/mytv-flux/app/strategie.py `decider`, main.py `live_transcode`, sonde.py, config.py) : l'ancien service SONDAIT chaque chaine et choisissait : h264+aac -> playlist reecrite ; audio ac3/eac3/dts/mp2 -> ffmpeg copie la video et reencode l'audio en AAC ; HEVC <= 1080p -> reencodage x264 (veryfast, crf 23, ~1 coeur) ; HEVC > 1080p (4K) -> REFUS avec message. mytv ne fait AUCUNE conversion du direct : les chaines EAC3 / HEVC sont injouables (fragParsingError en boucle, 2946 erreurs et 190 abandons mesures). Les chaines 4K (CANAL+ 4K : HEVC Main10 3840x2160 + EAC3, 16 Mo/segment) etaient deja refusees avant : elles doivent l'etre avec un message clair.
Regles inchangees : docs/processus.md, CA numerotes couverts par de VRAIS tests (commentaire « CA3 »), verification par mutation que les tests de correction echouent sans le correctif, gofmt/vet/`go test -race ./...` verts, aucun secret ni URL fournisseur dans journaux/erreurs/ARGV de processus, reglages dans internal/config avec validation testee. Production : service `mytv` (NE PAS le toucher), /etc/mytv, /var/lib/mytv (la vraie base), Caddy, tunnel : interdits. Tests = faux fournisseur uniquement. ffmpeg/ffprobe sont installes (/usr/bin).
Worktrees : /opt/mytv-work/c5-a (Go, feat/lot5-a), /opt/mytv-work/c5-b (Go, feat/lot5-b), /opt/mytv-work/ui-1 (UI, feat/ui-1, `NODE_OPTIONS=--tls-max-v1.2`).

## US-30 — Sonde et decision du direct (codeur c5-a) · A FAIRE · PRIORITE 1
- CA1 Sonde d'une chaine : ffprobe sur UN segment recupere par le relais (jamais l'URL fournisseur ni les identifiants dans argv : source locale a usage unique, comme internal/remux/fluxsonde.go) ; prend le bail ; une seule sonde a la fois ; resultat (codec video, hauteur, codec audio) en cache `live.duree_sonde` (defaut 10 min) ; un echec de sonde n'interdit pas la lecture (repli : relais brut) ; singleflight par chaine.
- CA2 Decision pure et testee (table de cas) `DeciderLive` : h264+aac/mp3 -> direct (relais actuel) ; audio ac3/eac3/dts/truehd/mp2 -> `audio` (video copy, audio aac 192k stereo) ; HEVC (ou autre non h264) avec hauteur <= `live.hauteur_max_reencodage` (defaut 1080) et `live.reencodage_video` vrai -> `video` (x264 veryfast crf 23, GOP regulier) ; au-dela ou reencodage interdit -> refus `format_hevc_non_lisible` (415) avec message nommant le codec et la hauteur ; flux audio seul -> direct ; defauts et validation dans internal/config.
- CA3 Le mode decide est visible : en-tete `X-Mytv-Mode` (direct|audio|video|refus) sur la playlist, et `X-Mytv-Codec`/hauteur utilises par l'interface ; contrat docs/openapi.yaml + test de conformite.
- CA4 `?forcer=audio|video` (jamais `direct`/`refus`) impose le mode quand la sonde se trompe ; refuse hors liste ; documente.
## US-31 — Transcodeur du direct (codeur c5-a, apres US-30) · A FAIRE
- CA1 ffmpeg lit l'amont via une source locale a usage unique 127.0.0.1 alimentee par le client fournisseur filtre (hotes, Range/reprise comme US-17) ; AUCUNE URL ni identifiant dans argv (test comme US-17) ; produit un HLS (segments 4 s, liste 6, delete_segments) dans un dossier temporaire par chaine sous `live.dossier_hls` (defaut `hls_live/` relatif au WorkingDirectory), servi par la route live avec jetons signes (liaison a la chaine), URL de segments stables pour hls.js.
- CA2 Un seul transcodage a la fois (`remux.processus_max`, defaut 2 pour tout, mais le direct n'en utilise qu'un) ; zapping : l'ancien est arrete et son dossier supprime avant de demarrer le nouveau ; fin de lecture (`POST /live/{chaine}/fin`), depart du client, inactivite (`live.inactivite_transcodage`, defaut 60 s) ou arret du service : processus tue (groupe de processus, SIGTERM puis SIGKILL), dossier nettoye ; au demarrage, dossiers orphelins supprimes.
- CA3 Le bail est renouvele tant que ffmpeg tourne ; patience 407 comme le direct ; une panne ffmpeg au demarrage -> 502 `transcodage_impossible` (code stable) et repli propre ; delai de demarrage borne (`live.delai_demarrage_transcodage`).
- CA4 Tests (ffmpeg local, `t.Skip` si absent) : faux fournisseur servant un MPEG-TS genere par ffmpeg (HEVC 640x360+eac3 ; h264+ac3 ; h264+aac), sortie verifiee par ffprobe (h264 + aac), un seul ffmpeg vivant, zero processus et zero dossier apres fin/zapping/arret, annulation, aucune URL/identifiant dans argv ; mutation : echec sans le correctif.
- CA5 Mesures consignees dans docs/exploitation.md : delai de demarrage et CPU pour audio et video (HEVC 640x360 en test) ; avertissement documente sur le cout du mode video (~1 coeur).

## Ajout (decision du 2026-10-16) — Negociation des capacites du navigateur
L'utilisateur regarde sur Firefox, Chrome et Edge. Firefox ne decode pas l'HEVC ; Chrome/Edge (Windows, decodeur materiel) peuvent decoder HEVC et parfois EAC3/AC3 (Edge avec extensions Microsoft). La conversion serveur est couteuse (reencodage ~1 coeur) : elle ne doit servir QUE si le navigateur ne sait pas lire la source. La 4K HEVC doit donc jouer en direct sur un navigateur capable, et n'etre refusee que pour un navigateur incapable.
- US-30 CA5 (c5-a) : la decision prend en compte les CAPACITES du client, annoncees par l'en-tete `X-Mytv-Capacites` (liste separee par des virgules parmi `hevc`, `eac3`, `ac3`) ou le parametre `?cap=hevc,eac3` (hls.js ne permet pas toujours d'ajouter des en-tetes aux requetes de playlist : accepter les deux) ; valeurs inconnues ignorees ; absence = navigateur SUPPOSE incapable de tout sauf h264+aac. Table de decision : h264+aac -> direct ; audio eac3/ac3 et client capable -> direct sinon `audio` ; HEVC et client `hevc` -> direct (aucune conversion, y compris 4K) sinon `video` si <= hauteur_max_reencodage sinon refus `format_hevc_non_lisible` ; le mode et les capacites utilisees sont journalises et exposes (`X-Mytv-Mode`). Le cache de decision est par (chaine, capacites). Tests : table complete de la decision avec et sans capacites ; mutation.
- US-32 CA5 (c5-b, interface) : au demarrage la page DETECTE ses capacites reelles par `MediaSource.isTypeSupported` / `MediaCapabilities.decodingInfo` (video/mp4 codecs hvc1.2.4.L153.B0 et hev1 pour HEVC Main10 4K, audio/mp4 codecs ec-3 et ac-3, et un test de lecture plausible : `supported && smooth/powerEfficient` pour la 4K), les annonce a CHAQUE requete de playlist/segment du direct et des films (`?cap=` ou en-tete), les memorise (localStorage avec repli) et les journalise dans la telemetrie (navigateur, version, capacites) ; si hls.js ne peut pas lire l'HEVC TS meme quand le navigateur l'annonce (erreur fragParsingError / bufferAppend), repli : une tentative sans la capacite `hevc` (le serveur convertit ou refuse proprement) puis message ; tests unitaires de la detection (doublures de MediaSource) et du repli ; aucun test sur un vrai flux.
- US-31 CA6 (c5-a) : en mode `direct` pour un client capable, la 4K HEVC passe par le relais existant (aucun ffmpeg) : test de non-regression de performance (zero processus) et de debit.
