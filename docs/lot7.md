# Lot 7 — Lenteurs mesurees : catalogue, playlists du fournisseur, mode economie, recommandation

Constats (journal mytv et telemetrie du lecteur, 2026-10-20 -> 2026-10-27, UTC) :
- **Catalogue** : la version du manifeste est l'HEURE de synchronisation (internal/api/export.go versionCatalogue). Chaque matin apres 05:00, tous les appareils retelechargent 17 Mo compresses (live 1,5 + films 12,3 + series 3) et reimportent ~154 000 entrees dans IndexedDB : 12 s mesurees dans Chromium sur le serveur, 30 s a 1 min sur un PC distant (tunnel 5-15 Mbit/s), bien plus sur un iPhone. Le 2026-10-21 a 05:00 le fournisseur a renvoye 0 film : la synchronisation a ETE ECRITE (films absents toute la journee), donc deux reimports complets de plus.
- **Fournisseur, serveur central** : RTT 103 ms mais 0,5 s de traitement par requete (player_api TTFB 0,62 s). Playlist mediane 765 ms, p90 1 s ; 225 echecs « context deadline exceeded » (4 s) en 7 jours, 23 % des playlists entre 21 h et 22 h, 11 % a 06 h. Ouverture d'une chaine (1re demande -> 1er segment servi) : mediane 1,5 s, mais 10, 16, 22, 31, 95 s aux heures de pointe (chaine 1410044 : 13 delais de 4 s d'affilee le 25/10 a 21:30, puis « playlist indisponible »).
- **Liaison du spectateur** : a la maison 28-37 Mbit/s mesures par le lecteur, segments en 1,3-2,4 s, pas de blocage. Le PC Windows (Firefox) en soiree : debit p10 3,2 Mbit/s, p25 5 Mbit/s, segment p90 10,6 s pour 10 s de video, 41 blocages (`video:waiting`) en 2 h. iPhones a 0,5-7 Mbit/s : blocages a chaque segment. Un flux HD a 5,4 Mbit/s ne passe pas sur ces liaisons ; une seule rendition, hls.js ne peut rien adapter.
- Ce qui n'est PAS lent : API locale (compte 1 ms, recherche 13 ms, export live 309 ms, fiches films/series 0,2-0,7 s au premier appel puis 1 ms), segments a la maison, sauvegarde, EPG.

## US-36 — Catalogue : version stable, synchronisation vide refusee, import par difference (codeur c7-a, Go + UI) · A FAIRE
- CA1 La version du manifeste depend du CONTENU, pas de l'heure : empreinte (SHA-256 tronquee) calculee a l'ecriture du catalogue sur les identifiants, noms, categories, logos et champs exportes de chaque entree, stockee dans `synchros` (migration SQLite) ; une synchronisation qui ne change rien garde la meme version ; les images/logos EPG continuent d'entrer dans l'empreinte comme aujourd'hui. Test : deux synchronisations identiques -> meme version ; une entree modifiee -> version differente ; mutation verifiee.
- CA2 Garde contre une synchronisation degradee : si le nouveau catalogue perd plus de `catalogue.perte_max` (defaut 50 %) des chaines, films OU series par rapport au precedent (ou tombe a 0 alors que l'ancien en avait), il est REFUSE (ancien conserve, WARN « catalogue degrade refuse » avec les comptes, metrique `synchro_total{resultat=refus_degrade}`, supervision/webhook informes comme pour un echec) ; une base vide (premier import) accepte tout. Test sur le cas reel du 21/10 (films 0) ; mutation verifiee.
- CA3 Export par difference : `GET /api/v1/catalogue/export?type=...&depuis=<version>` renvoie seulement les entrees ajoutees/modifiees depuis cette version et la liste des identifiants supprimes (`X-Supprimes` ou premiere ligne NDJSON de type `suppressions`), a partir d'un journal de differences conserve `catalogue.historique_versions` versions (defaut 14) ; version inconnue ou trop ancienne -> 409 `version_inconnue` et le client refait un import complet. Contrat docs/openapi.yaml + test de conformite.
- CA4 Interface (src/lib/plan-import.ts, catalogue.ts, import.worker.ts) : quand la version change, import par difference si le serveur le propose, complet sinon ; progression affichee ; mesure envoyee en telemetrie (`catalogue:import` : mode, entrees, ms) ; tests unitaires du plan (meme version -> rien ; version connue -> difference ; 409 -> complet) ; e2e sur serveur factice ; mutation verifiee.
- CA5 Aucune regression : import complet initial inchange (mesure de reference : 154 686 entrees en 12 s dans Chromium local), `go test -race ./...` et 134+ tests UI verts.

## US-37 — Direct : playlists lues sur le noeud de diffusion, pas sur le serveur central (codeur c7-b, Go) · A FAIRE
- CA1 Apres la premiere playlist d'une chaine (302 du central vers un noeud), le relais RETIENT l'adresse finale par chaine et y recharge directement les playlists suivantes (comme un lecteur TS continu) ; retention bornee `live.retention_noeud` (defaut 10 min, validee > 0) ; a tout echec sur le noeud (delai, 5xx, 401/403/404, corps sans `#EXTM3U`) : oubli immediat et retour au central avec les essais/patience actuels, sans consommer la patience pour l'echec du noeud ; metriques `live_playlists_noeud_total{resultat=ok|repli}`. Test avec `fauxiptv` (redirections comptees : 1 seule pour N playlists ; noeud tue -> repli en < 1 s) ; mutation verifiee.
- CA2 Les segments continuent d'etre resolus comme aujourd'hui (table des noms, jetons) ; la continuite (internal/live/continuite.go) et la detection de redemarrage restent valides quand l'adresse change de noeud (nouveau noeud = memes regles « memes segments / nouveaux segments »). Tests existants verts + un test « changement de noeud sans redemarrage ».
- CA3 Le mode conversion (transcodage.go, boucle amont qui alimente ffmpeg) utilise le meme chemin ; aucune requete de plus vers le central pendant une conversion stable (compte des requetes du faux central = 1 par ouverture).
- CA4 Exploitation : reglage documente ; `GET /admin/fournisseurs` ou `/live/etat` expose le nombre de playlists servies depuis un noeud et de replis ; journal INFO a chaque repli (chaine, cause, sans URL).

## US-38 — Mode economie : conversion a debit reduit a la demande (codeur c7-b, Go, puis ui-3) · A FAIRE
- CA1 Parametre de lecture `qualite=eco` (query ou en-tete `X-Mytv-Qualite`) sur la playlist du direct : la decision (internal/live/decision.go) passe en mode video avec cible `live.eco.hauteur` (defaut 480) et `live.eco.debit_kbps` (defaut 1200, audio 96 kbps AAC), quel que soit le codec source (H.264 compris), sous les memes bornes CPU que la conversion actuelle (`processus_max`, file) ; sans le parametre : comportement inchange. Validation de config (hauteur 240-1080, debit 300-6000). Test : arguments ffmpeg attendus (`-vf scale=-2:480`, `-b:v`, `-maxrate`, `-bufsize`, `-b:a`) ; mutation verifiee.
- CA2 Films et series : `qualite=eco` sur `/vod/...` force le remux en reencodage video a la meme cible (y compris MP4 H.264 direct) ; `X-Mytv-Mode` l'indique ; test avec vrai ffmpeg sur un fichier genere (hauteur de sortie verifiee par ffprobe).
- CA3 Un changement de qualite en cours de lecture rouvre proprement (ancien ffmpeg arrete, un seul processus par session) ; test existant « un seul processus » etendu.
- CA4 UI (ui-3) : bouton « Qualite : Auto / Eco » dans le lecteur et les Reglages (valeur memorisee par appareil, `localStorage`) ; « Eco » ajoute le parametre a toutes les ouvertures ; recommandation automatique « Passer en Eco ? » quand le debit mesure (`hls:segment debitKbps`, mediane glissante sur 5 segments) est inferieur a 1,5x le debit du flux pendant 30 s, avec un seul rappel par lecture ; tests unitaires de la regle ; mutation verifiee.

## US-39 — Recommandation de la meilleure facon de regarder une chaine (codeur ui-3, UI + Go leger) · A FAIRE
- CA1 Regroupement des variantes : les chaines dont le nom normalise est identique (suppression des prefixes pays « FR - », « FR: », des suffixes de qualite « 4K », « UHD », « FHD », « HD », « SD », « ᴴᴰ », « HEVC », « H265 », « (backup) », des espaces et de la casse) forment un GROUPE ; la liste du Direct affiche une seule ligne par groupe avec ses variantes ; fonction pure `grouperVariantes` testee sur 30 libelles reels du catalogue (fichier de cas) ; une chaine sans variante reste telle quelle.
- CA2 Score de fluidite par variante et par contexte (appareil + classe de debit : <5, 5-15, >15 Mbit/s) a partir de la telemetrie DEJA collectee par le lecteur (blocages par heure de lecture, erreurs, debit, redemarrages) : calcule cote client (IndexedDB, fenetre glissante 14 jours) ; pas de connexion supplementaire au fournisseur ; tests unitaires du score (cas : variante qui bloque 3 fois/h vs 0).
- CA3 Choix a l'ouverture : la variante recommandee = meilleure note parmi celles lisibles par le navigateur (capacites : HEVC, EAC3, 4K refusee si `hauteur_max`), avec le debit mesure courant ; affichage d'une ligne dans le lecteur (« Recommande : HD — fluide sur cette liaison. 4K deconseillee : liaison a 10 Mbit/s ») ; l'utilisateur peut choisir une autre variante (menu), et son choix explicite est retenu pour le groupe. Sans historique : ordre par defaut = la plus haute definition compatible avec le debit mesure (regle : 4K >= 20 Mbit/s, FHD >= 8, HD >= 4, sinon SD/Eco).
- CA4 Test actif a la demande (bouton « Tester cette chaine ») : enchaine les variantes UNE par UNE (jamais deux flux), 1 playlist + 1 segment chacune, affiche latence et debit par variante, resultat garde 24 h ; refuse de se lancer si une lecture est en cours ailleurs dans mytv (reponse `compte_utilise_par_mytv`) ; e2e sur serveur factice.
- CA5 Telemetrie `recommandation:choix` (groupe, variante recommandee, variante choisie, raison) ; aucun secret ; `npm run build` vert.

Ordre : US-36 CA1-CA2 et US-37 d'abord (gains immediats, sans changement d'interface visible), puis US-38, puis US-39.
